## [0.5.0] - 2026-09-21

### 🎉 MVP 1 Complete

Completed the first functional MVP of VeteApp, connecting the main veterinary
workflows to the BFF and SQLite persistence.

The application now supports persistent client, pet, appointment, appointment
status, and clinical consultation data across the main Reception, Agenda,
Clients, and Clinical History flows.

### ✨ Added

#### Appointments persistence

- Added SQLite persistence for appointments.
- Added `appointments` relational table.
- Added foreign key relationship between appointments and pets.
- Added appointment IDs generated by SQLite.
- Added persisted appointment status lifecycle.
- Added appointment lookup with joined pet and client information.

#### Appointments API

- Added `GET /appointments`.
- Added `POST /appointments`.
- Added `PATCH /appointments/:id/status`.
- Added appointment repository, service, controller, and routes.
- Added appointment creation using persisted pet IDs.
- Added appointment status updates in SQLite.
- Added full appointment responses including patient and responsible person data.

#### Frontend appointment integration

- Added frontend appointment service layer.
- Connected appointment loading to `GET /appointments`.
- Connected appointment creation to `POST /appointments`.
- Connected appointment status changes to `PATCH /appointments/:id/status`.
- Replaced appointment mock initialization with persisted BFF data.
- Integrated persisted appointments with `AppointmentsProvider`.
- Added immediate Context synchronization after appointment creation.
- Added immediate Context synchronization after appointment status updates.
- Added appointment creation for existing persisted patients.
- Added appointment creation flow for new clients and pets.
- Added appointment creation from Client Detail and Reception flows.
- Added persisted `petId` propagation across appointment navigation flows.

#### Agenda

- Added appointment search by patient name, responsible person, or DNI.
- Added normalized search support for names and DNI values.
- Added DNI search with or without formatting characters.
- Added persisted appointment status changes.
- Added date-based appointment filtering.
- Added appointment pagination.
- Added appointment status sorting.

#### Clinical history persistence

- Added SQLite persistence for clinical consultations.
- Added `consultations` relational table.
- Added foreign key relationship between consultations and pets.
- Added consultation IDs generated by SQLite.
- Added consultation repository, service, controller, and routes.

#### Clinical consultations API

- Added `GET /consultations`.
- Added `POST /consultations`.
- Added persisted consultation creation.
- Added consultation retrieval from SQLite.

#### Frontend clinical history integration

- Added frontend consultation service layer.
- Connected consultation loading to `GET /consultations`.
- Connected consultation creation to `POST /consultations`.
- Replaced consultation mock initialization with persisted BFF data.
- Integrated persisted consultations with `ConsultationsProvider`.
- Added immediate Context synchronization after consultation creation.
- Removed frontend-generated consultation IDs.
- Added persisted clinical history per patient.

#### Form validation

- Added validation to the new consultation flow.
- Added required validation for consultation reason and diagnosis.
- Added minimum-length validation for required clinical fields.
- Added touched-state validation feedback.
- Added reusable error support to the `Textarea` component.
- Added error propagation through the reusable `InputText` component.
- Prevented invalid consultation forms from being submitted.

### ♻️ Changed

#### Appointment state

- Replaced frontend appointment mock data with data loaded from the BFF.
- Changed appointment status updates from local-only state changes to persisted API operations.
- Kept `AppointmentsContext` as shared UI state while SQLite acts as the persistent source of truth.
- Changed appointment creation to use persisted client and pet relationships.
- Removed frontend responsibility for generating appointment IDs.

#### Clinical history state

- Replaced frontend consultation mock data with data loaded from the BFF.
- Kept `ConsultationsContext` as shared UI state while SQLite acts as the persistent source of truth.
- Moved consultation ID generation from the frontend to SQLite.
- Normalized optional treatment and observation values returned by the BFF.

#### Architecture

- Extended the existing layered BFF architecture to appointments and consultations.
- Extended SQLite persistence across all MVP 1 core entities.
- Consolidated the application data flow around:

  `React → Context → Frontend Service → REST API → Route → Controller → Service → Repository → SQLite`

- Established SQLite as the persistent source of truth for clients, pets, appointments, appointment statuses, and clinical consultations.
- Kept React Context responsible for current application state and immediate UI synchronization.

### 🛠️ Fixed

#### Appointments

- Fixed appointments disappearing after browser refresh.
- Fixed appointment status changes reverting to `pending` after browser refresh.
- Fixed appointment status inconsistencies between Agenda and Reception.
- Fixed newly created appointments requiring a browser refresh before appearing in Agenda.
- Fixed appointment creation for existing patients by propagating persisted `petId`.
- Fixed appointment creation from Client Detail.
- Fixed appointment creation from Reception search results.
- Fixed appointment creation for new clients and pets from Agenda.
- Fixed appointment POST responses so they return complete patient and responsible person data.

#### Agenda

- Fixed appointment search by patient name.
- Fixed appointment search by responsible person.
- Fixed appointment search by DNI.
- Fixed DNI search when entering the number without formatting characters.
- Fixed search pagination reset when the search value changes.

#### Clinical history

- Fixed clinical consultations being stored only in frontend state.
- Fixed clinical consultations disappearing after browser refresh.
- Fixed newly created consultations requiring local frontend-generated IDs.
- Fixed new consultations so they appear immediately in the patient's clinical history after creation.

#### Forms and Design System

- Fixed `InputText` so reusable input validation errors can be passed to the underlying `Input`.
- Added consistent validation feedback between `Input`, `InputText`, and `Textarea`.

### 🏁 MVP 1 Scope Completed

The first VeteApp MVP now includes:

- Reception dashboard and daily appointment visibility.
- Appointment management and appointment status lifecycle.
- Client search, creation, detail, and editing.
- Pet creation and editing.
- Appointment creation for existing and new patients.
- Clinical history search and patient clinical history.
- Clinical consultation registration.
- Persistent data across browser refreshes.
- Shared frontend state synchronized with the BFF.
- SQLite persistence for the core veterinary workflow.

### ⚠️ Known limitations

- Database schema creation is still handled directly during BFF initialization; a migration strategy has not yet been introduced.
- Appointment creation involving a new client and pet currently performs multiple sequential API requests and is not transactional.
- API-level validation and centralized error handling are still limited.
- Loading and error states are not yet standardized across all frontend views.
- Authentication, authorization, and user roles are intentionally outside the MVP 1 scope.
- Inventory, stock management, pet shop functionality, dashboards, and operational metrics are planned for a future MVP.


## [0.4.0] - 2026-09-21

### ✨ Added

#### BFF

- Added initial Node.js and Express BFF.
- Added layered backend architecture using Routes, Controllers, Services, and Repositories.
- Added mock data repository as the initial data source.
- Added JSON request body handling with Express.
- Added CORS configuration for communication between the React frontend and BFF.

#### Clients API

- Added `GET /clients`.
- Added `GET /clients/:id`.
- Added `POST /clients`.
- Added `PATCH /clients/:id`.
- Added `POST /clients/:clientId/pets`.
- Added `404` responses for non-existing clients.

#### Pets API

- Added `GET /pets/:petId`.
- Added `PATCH /pets/:petId`.
- Added global pet identifiers across clients.
- Added `404` responses for non-existing pets.

#### Frontend API integration

- Added frontend service layer for client and pet HTTP operations.
- Connected client loading to `GET /clients`.
- Connected client creation to `POST /clients`.
- Connected pet creation to `POST /clients/:clientId/pets`.
- Integrated BFF data with `ClientsProvider`.
- Added complete client and initial pet creation flow from `NewClientPage`.

### ♻️ Changed

#### Client state

- Replaced frontend client mock initialization with data loaded from the BFF.
- Kept `ClientsContext` as the shared application state for client-related views.
- Moved client and pet ID generation responsibility from the frontend to the BFF.
- Aligned the client data contract between the frontend and BFF.

#### Architecture

- Started migration from frontend-local mock data to BFF-managed application data.
- Introduced Repository abstraction to isolate data access from business and HTTP layers.
- Prepared the data layer for migration from in-memory mock data to persistent storage.

### 🛠️ Fixed

- Fixed client list rendering key warning.
- Fixed pet creation for existing clients.
- Fixed pet lookup using globally unique pet IDs.
- Fixed pet update flow using `PATCH /pets/:petId`.
- Fixed CORS errors between the frontend on port `3002` and BFF on port `3000`.

### ⚠️ Known limitations

- Client and pet data is currently stored in memory.
- Created or updated data is lost when the BFF process restarts.
- Persistent storage will be introduced in the next development stage.
